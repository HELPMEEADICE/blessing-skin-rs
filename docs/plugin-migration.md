# Legacy plugin migration tool

The Rust service does not load PHP plugins. `plugin-migrate` scans one legacy plugin directory and reports the PHP-specific work before producing an independent Rust component scaffold.

```powershell
cargo run --bin plugin-migrate -- path\to\plugin
cargo run --bin plugin-migrate -- path\to\plugin --output migration\my-plugin
```

The JSON report identifies PHP and Blessing Skin version requirements, dependencies on other PHP plugins, Composer packages, `enchants.providers` and `enchants.config` hooks, PHP source files, PHP-backed templates, and possible source-level dependencies on database, route, event, filesystem, network, and host-service APIs. Source findings include relative file paths and line numbers so maintainers can review each candidate. Detection is a case-insensitive literal scan, skips full-line comments, and can produce false positives or miss aliased and dynamically constructed calls. The scanner reads `package.json`, optional `composer.json`, and PHP source text; it does not execute plugin code or claim to translate PHP behavior.

When the output directory is supplied, it must be new or empty. The generated crate includes `migration-report.json`, a `wit-bindgen` guest, and the versioned `blessing-skin:plugin@1.0.0` contract. It imports `blessing-skin:plugin/host@1.0.0` and `blessing-skin:plugin/state@1.0.0`, and exports `blessing-skin:plugin/lifecycle@1.0.0` plus the optional `blessing-skin:plugin/events@1.0.0`, `blessing-skin:plugin/filters@1.0.0`, `blessing-skin:plugin/documentation@1.0.0`, and `blessing-skin:plugin/configuration@1.0.0`. Existing components without these optional exports continue to load. Logging accepts `trace`, `debug`, `info`, `warn`, and `error`, with each message limited to 4 KiB.

Host API version 1.9 adds the optional `blessing-skin:plugin/filters@1.0.0` export for `can_sign` and `sign_score`. The callback receives the filter name, current value, and user ID context as JSON strings; returning `none` keeps the value, while a JSON replacement is validated and passed to the next plugin in load order. A `can_sign` filter returns a boolean or `{ "rejection": "reason" }`; `sign_score` returns a signed integer. Host API version 1.10 adds `new_player_name` (string replacement) and `can_add_player` (boolean or rejection object); their context includes the user ID and proposed name. Host API version 1.11 adds `can_rename_player` with the current player record and proposed name, plus the `player.renaming` event. Host API version 1.12 adds `can_delete_player` with the current player record, plus `player.delete.attempt` before the filter and `player.deleting` after the filter but before the database delete. Host API version 1.15 adds `can_set_texture` and `can_clear_texture`; each receives the current player and texture type, `can_set_texture` also receives the requested texture ID, and a rejection object denies the operation. Host API version 1.16 adds `user_can_update_avatar` with the user ID and requested texture ID as context; a rejection object prevents the update. Host API version 1.17 adds `user_can_edit_profile` with user ID and action context. Passwords, email addresses, and other submitted credentials are excluded from this context. Guest traps, invalid JSON or types, and checkpoint errors roll back that plugin call and preserve the preceding value. Existing components without the optional filters export remain loadable. The versioned contract is maintained at [plugins/sdk/wit/world.wit](../plugins/sdk/wit/world.wit). [plugins/examples/player-counter](../plugins/examples/player-counter) is a buildable guest example that persists a count of player.added events; CI verifies that its contract and generated migration scaffolds match the SDK contract.

The generated guest shows how to persist a first-run marker with `state.get` and `state.set`. The state interface provides `get`, `set`, and `delete` over binary values isolated by plugin name. Keys are limited to 128 bytes; a plugin may store at most 256 keys, 64 KiB per value, and 1 MiB total. State is checkpointed after `initialize`, after successful event callbacks that change state, and after a successful `shutdown`. Host API version 1.11 adds `player.renaming` with `{ "user_id": number, "player_id": number, "previous_name": string, "name": string }`, emitted after name filtering and before permission checks on self-service renames, and before the database update on admin renames. Host API version 1.12 adds `player.delete.attempt` and `player.deleting` with `{ "user_id": number, "player_id": number, "name": string }`; the first runs before `can_delete_player` and the second runs after the filter but before deletion. Host API version 1.13 adds `player.texture.updating` before the texture existence check, with `{ "user_id": number, "player_id": number, "name": string, "type": string, "texture_id": number }`, and `player.texture.updated` after the database update, with `{ "user_id": number, "player_id": number, "name": string, "type": string, "previous_texture_id": number, "texture_id": number }`. Host API version 1.14 adds `player.owner.updating` with `{ "player_id": number, "previous_user_id": number, "user_id": number }`, emitted before checking the destination user and before transferring ownership. Host API version 1.15 adds `player.texture.resetting` before each selected field is cleared, with `{ "user_id": number, "player_id": number, "name": string, "type": string, "texture_id": number }`, and `player.texture.reset` after the database update, with `{ "user_id": number, "player_id": number, "name": string, "type": string, "previous_texture_id": number, "texture_id": number }`. Host API version 1.16 adds `user.avatar.updating` before texture validation and `user.avatar.updated` after the database update, both with `{ "user_id": number, "texture_id": number }`. Host API version 1.18 adds `user.profile.updating` with `{ "user_id": number, "action": string }` before profile action validation and `user.deleting` with `{ "user_id": number }` before account deletion. Host API version 1.10 adds `player.add.attempt` and `player.adding` with `{ "user_id": number, "name": string }`; the former runs after name filters and before permission filters, and the latter runs after the score check but before insertion. Host API version 1.8 adds `user.sign.before` and `user.sign.after` with `{ "user_id": number, "score": number }`; `score` is the selected reward, and the events run before the database update and after a successful update, respectively. Host API version 1.7 adds `user.logged-out` with `{ "user_id": number }`, emitted after an authenticated session is cleared. Host API version 1.6 adds closet.added and closet.renamed events with { "user_id": number, "texture_id": number, "item_name": string }, plus closet.removed with { "user_id": number, "texture_id": number }. Host API version 1.5 added optional documentation and JSON configuration exports. Host API version 1.4 added administrative user verification, permission, and score events alongside player ownership and texture assignment events; both releases keep the lifecycle, logging, state, and events interface versions stable. The event callback receives a name and UTF-8 JSON object bytes, capped at 64 KiB. Events include `user.logged-in`, `user.logged-out`, `user.registered`, and `user.deleting` / `user.deleted` with `{ "user_id": number }`; `user.verification.updated` with `{ "user_id": number, "previous_verified": boolean, "verified": boolean }`; `user.profile.updating` with `{ "user_id": number, "action": string }` / `user.profile.updated` with `{ "user_id": number, "action": "nickname" | "password" | "email" }`; `user.avatar.updating` / `user.avatar.updated` with `{ "user_id": number, "texture_id": number }`; `player.added` / `player.deleted` / `player.delete.attempt` / `player.deleting` with `{ "user_id": number, "player_id": number, "name": string }`; and `player.renamed` with `{ "user_id": number, "player_id": number, "previous_name": string, "name": string }`; `player.owner.updating` / `player.owner.updated` with `{ "player_id": number, "previous_user_id": number, "user_id": number }`; and `player.textures.updated` with `{ "user_id": number, "player_id": number, "skin_texture_id": number, "cape_texture_id": number }`. `player.texture.updating` with `{ "user_id": number, "player_id": number, "name": string, "type": string, "texture_id": number }`; `player.texture.updated` with `{ "user_id": number, "player_id": number, "name": string, "type": string, "previous_texture_id": number, "texture_id": number }`; `player.texture.resetting` with `{ "user_id": number, "player_id": number, "name": string, "type": string, "texture_id": number }`; `player.texture.reset` with `{ "user_id": number, "player_id": number, "name": string, "type": string, "previous_texture_id": number, "texture_id": number }`; Texture lifecycle events are `texture.uploaded` with `{ "user_id": number, "texture_id": number, "hash": string, "name": string, "type": string, "public": boolean }`, `texture.renamed` with `{ "texture_id": number, "previous_name": string, "name": string }`, `texture.deleted` with `{ "texture_id": number, "uploader_id": number, "hash": string, "name": string }`, `texture.visibility.updated` with `{ "texture_id": number, "public": boolean }`, and `texture.type.updated` with `{ "texture_id": number, "previous_type": string, "type": string }`; `notification.sent` with `{ "sender_id": number, "recipient_id": number, "notification_id": string }`; `notification.read` with `{ "user_id": number, "notification_id": string }`; `report.submitted` with `{ "reporter_id": number, "texture_id": number, "uploader_id": number }`; and `report.reviewed` with `{ "report_id": number, "admin_user_id": number, "action": "reject" | "ban" | "delete", "status": number }`. Notification content and report reasons are not included. Passwords, email addresses, and other submitted credentials are never included. The optional documentation export returns Markdown for `/admin/plugins/readme/{name}`; the optional configuration export provides `get` and `set` JSON object strings for `/admin/plugins/config/{name}`. Configuration is limited to 64 KiB and persisted in the plugin-scoped state table with rollback when validation or checkpointing fails. Filter callbacks run before their relevant business write; their plugin state remains checkpointed if that write later fails. Post-operation event callbacks run after the underlying operation succeeds, except `user.sign.before`, which reports the selected reward immediately before the update. Callback failures are logged and isolated from the HTTP response; changes to plugin state are rolled back on callback or checkpoint failure.

Super administrators can install a component by uploading its WASM file or by entering a public HTTPS URL ending in .wasm in the admin plugin page. Remote downloads follow at most five redirects and recheck each destination; private and special-use IP ranges are rejected, and responses are capped at 32 MiB before component validation. Direct uploads and URL installs never overwrite existing plugin files. The configured versioned WASM registry supports explicit, checksum-verified updates with a backup-and-restore file replacement; the current process keeps executing the loaded component until restart. ZIP archives and PHP plugins are not installed by these paths. Build the component with `cargo component build --release`, then place the resulting `.wasm` component under `PLUGINS_DIR`. The host creates the Rust-only `{prefix}wasm_plugin_state` table idempotently when loading components; new installs create it with the initial schema. To roll back, stop the Rust service and remove that table after saving or discarding plugin state. No legacy PHP table is altered. The legacy Artisan command names `plugin:enable <name>` and `plugin:disable <name>` are available in the Rust binary for WASM components; they rename `<name>.wasm` and `<name>.wasm.disabled` in `PLUGINS_DIR`. Restart the service for the changed plugin state to take effect.

The host does not expose filesystem, network, raw database, WASI, or arbitrary host imports. Components run with fuel, memory, table, and file-size limits. Plugins cannot register HTTP routes or access arbitrary Blessing Skin business data; event payloads are limited to the documented fields. New host capabilities require an explicit versioned WIT interface and must preserve the sandbox boundary.

See the [Bytecode Alliance Rust component guide](https://component-model.bytecodealliance.org/language-support/building-a-simple-component/rust.html) for the WIT and `wit-bindgen` component workflow.
