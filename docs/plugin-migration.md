# Legacy plugin migration tool

The Rust service does not load PHP plugins. `plugin-migrate` scans one legacy plugin directory and reports the PHP-specific work before producing an independent Rust component scaffold.

```powershell
cargo run --bin plugin-migrate -- path\to\plugin
cargo run --bin plugin-migrate -- path\to\plugin --output migration\my-plugin
```

The JSON report identifies PHP and Blessing Skin version requirements, dependencies on other PHP plugins, Composer packages, `enchants.providers` and `enchants.config` hooks, PHP source files, and PHP-backed templates. The scanner reads `package.json`, optional `composer.json`, and filenames; it does not execute plugin code or claim to translate PHP behavior.

When the output directory is supplied, it must be new or empty. The generated crate includes `migration-report.json`, a `wit-bindgen` guest, and the versioned `blessing-skin:plugin@1.0.0` contract. It imports `blessing-skin:plugin/host@1.0.0` and `blessing-skin:plugin/state@1.0.0`, and exports `blessing-skin:plugin/lifecycle@1.0.0` plus the optional `blessing-skin:plugin/events@1.0.0`, `blessing-skin:plugin/documentation@1.0.0`, and `blessing-skin:plugin/configuration@1.0.0`. Existing components without these optional exports continue to load. Logging accepts `trace`, `debug`, `info`, `warn`, and `error`, with each message limited to 4 KiB.

The versioned contract is maintained at [plugins/sdk/wit/world.wit](../plugins/sdk/wit/world.wit). [plugins/examples/player-counter](../plugins/examples/player-counter) is a buildable guest example that persists a count of player.added events; CI verifies that its contract and generated migration scaffolds match the SDK contract.

The generated guest shows how to persist a first-run marker with `state.get` and `state.set`. The state interface provides `get`, `set`, and `delete` over binary values isolated by plugin name. Keys are limited to 128 bytes; a plugin may store at most 256 keys, 64 KiB per value, and 1 MiB total. State is checkpointed after `initialize`, after successful event callbacks that change state, and after a successful `shutdown`. Host API version 1.7 adds `user.logged-out` with `{ "user_id": number }`, emitted after an authenticated session is cleared. Host API version 1.6 adds closet.added and closet.renamed events with { "user_id": number, "texture_id": number, "item_name": string }, plus closet.removed with { "user_id": number, "texture_id": number }. Events fire after the database operation succeeds; admin closet mutations identify the affected user as user_id. Host API version 1.5 added optional documentation and JSON configuration exports. Host API version 1.4 added administrative user verification, permission, and score events alongside player ownership and texture assignment events; both releases keep the lifecycle, logging, state, and events interface versions stable. The event callback receives a name and UTF-8 JSON object bytes, capped at 64 KiB. Events include `user.logged-in`, `user.logged-out`, `user.registered`, and `user.deleted` with `{ "user_id": number }`; `user.verification.updated` with `{ "user_id": number, "previous_verified": boolean, "verified": boolean }`; `user.permission.updated` with `{ "user_id": number, "previous_permission": number, "permission": number }`; and `user.score.updated` with `{ "user_id": number, "previous_score": number, "score": number }`, emitted after administrator score changes and successful sign-in rewards; `user.profile.updated` with `{ "user_id": number, "action": "nickname" | "password" | "email" }`; `user.avatar.updated` with `{ "user_id": number, "texture_id": number }`; `player.added` / `player.deleted` with `{ "user_id": number, "player_id": number, "name": string }`; and `player.renamed` with `{ "user_id": number, "player_id": number, "previous_name": string, "name": string }`; `player.owner.updated` with `{ "player_id": number, "previous_user_id": number, "user_id": number }`; and `player.textures.updated` with `{ "user_id": number, "player_id": number, "skin_texture_id": number, "cape_texture_id": number }`. Texture lifecycle events are `texture.uploaded` with `{ "user_id": number, "texture_id": number, "hash": string, "name": string, "type": string, "public": boolean }`, `texture.renamed` with `{ "texture_id": number, "previous_name": string, "name": string }`, `texture.deleted` with `{ "texture_id": number, "uploader_id": number, "hash": string, "name": string }`, `texture.visibility.updated` with `{ "texture_id": number, "public": boolean }`, and `texture.type.updated` with `{ "texture_id": number, "previous_type": string, "type": string }`; `notification.sent` with `{ "sender_id": number, "recipient_id": number, "notification_id": string }`; `notification.read` with `{ "user_id": number, "notification_id": string }`; `report.submitted` with `{ "reporter_id": number, "texture_id": number, "uploader_id": number }`; and `report.reviewed` with `{ "report_id": number, "admin_user_id": number, "action": "reject" | "ban" | "delete", "status": number }`. Notification content and report reasons are not included. Passwords, email addresses, and other submitted credentials are never included. The optional documentation export returns Markdown for `/admin/plugins/readme/{name}`; the optional configuration export provides `get` and `set` JSON object strings for `/admin/plugins/config/{name}`. Configuration is limited to 64 KiB and persisted in the plugin-scoped state table with rollback when validation or checkpointing fails. Callbacks run only after the underlying operation succeeds. Callback failures are logged and isolated from the HTTP response; changes to plugin state are rolled back on callback or checkpoint failure.

Super administrators can install a component by uploading its WASM file or by entering a public HTTPS URL ending in .wasm in the admin plugin page. Remote downloads follow at most five redirects and recheck each destination; private and special-use IP ranges are rejected, and responses are capped at 32 MiB before component validation. Direct uploads and URL installs never overwrite existing plugin files. The configured versioned WASM registry supports explicit, checksum-verified updates with a backup-and-restore file replacement; the current process keeps executing the loaded component until restart. ZIP archives and PHP plugins are not installed by these paths. Build the component with `cargo component build --release`, then place the resulting `.wasm` component under `PLUGINS_DIR`. The host creates the Rust-only `{prefix}wasm_plugin_state` table idempotently when loading components; new installs create it with the initial schema. To roll back, stop the Rust service and remove that table after saving or discarding plugin state. No legacy PHP table is altered.

The host does not expose filesystem, network, raw database, WASI, or arbitrary host imports. Components run with fuel, memory, table, and file-size limits. Plugins cannot register HTTP routes or access arbitrary Blessing Skin business data; event payloads are limited to the documented fields. New host capabilities require an explicit versioned WIT interface and must preserve the sandbox boundary.

See the [Bytecode Alliance Rust component guide](https://component-model.bytecodealliance.org/language-support/building-a-simple-component/rust.html) for the WIT and `wit-bindgen` component workflow.
